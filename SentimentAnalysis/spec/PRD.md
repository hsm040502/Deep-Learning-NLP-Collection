# 產品需求文件 (PRD): 基於 RNN 的情感分析模型

## 1. 專案總覽與目標

本專案旨在開發一個基於循環神經網絡 (RNN) 的情感分析模型。該模型將使用 PyTorch 框架進行建置，並以 `data/Comments_Mobile_Phone.xml` 資料集進行訓練與評估。最終產出一個命令列工具 (CLI)，能夠分析輸入文字的情感傾向，並將其分類為「正面」、「負面」或「中性」。

**主要目標：**

*   從 XML 資料集中提取評論文字及其對應的真實情感標籤。
*   實作一個 LSTM (長短期記憶) 模型進行情感分析。
*   訓練模型以預測文字的情感分數 (0.0 至 1.0 之間)。
*   將預測的情感分數轉換為三分類標籤：正面 (1)、中性 (0)、負面 (-1)。
*   提供一個命令列介面，允許使用者分析 `data/Comments_Mobile_Phone.xml` 中的評論。
*   在命令列輸出每則評論的「真實情感分數」與「預測情感分數」。
*   計算並顯示整個模型在資料集上的「準確度 (Accuracy)」。

## 2. 目標使用者

本專案主要為**個人研究使用**，旨在探索與實作情感分析模型的開發流程。

## 3. 核心功能與實作細節

### 3.1. 資料載入與剖析

*   **需求 1 & 2：** 程式需能自動下載 (若本地不存在) 或讀取位於 `data/Comments_Mobile_Phone.xml` 的 3C 產品評論 XML 檔案。
*   使用 `BeautifulSoup` 或類似的 XML 剖析庫，解析 XML 內容。
*   提取每一則評論的文字內容 (例如，位於特定 XML 標籤內的文字)。
*   提取每一則評論對應的真實情感標籤。假設 XML 中 'positive' 標籤代表正面情感，'negative' 標籤代表負面情感。

### 3.2. 資料預處理

*   **需求 3 (部分)：** 對提取的評論文字進行以下預處理：
    *   **切分特徵 (X) 與標籤 (Y)：** 評論文字為 X，其對應的情感標籤為 Y。
    *   **斷詞 (Tokenization)：** 將評論文字切分成詞語序列。可考慮使用如 `spaCy`、`NLTK` 或基礎的以空格/標點符號分割的方法。
    *   **文字數位化 (Numericalization)：** 建立詞彙表 (vocabulary)，將詞語序列轉換為對應的數字索引序列。
    *   **序列對齊 (Padding/Truncation)：** 將所有數字索引序列處理成相同長度，以便輸入 LSTM 模型。不足長度的序列進行填充 (padding)，超過長度的進行截斷 (truncation)。

### 3.3. 模型建置與訓練 (LSTM)

*   **需求 2 (部分)：** 使用 PyTorch 框架建置一個 LSTM 模型。
    *   模型架構應包含嵌入層 (Embedding Layer)、LSTM 層，以及一個或多個全連接層 (Linear Layer) 用於最終的分類。
    *   輸出層的設計應能產生一個 0.0 至 1.0 之間的情感分數。
*   模型訓練：
    *   定義適當的損失函數 (例如，對於連續的情感分數，可以使用均方誤差 MSE Loss；若直接預測三分類，可使用交叉熵損失 CrossEntropyLoss)。
    *   選擇優化器 (例如 Adam, SGD)。
    *   在預處理後的資料集上進行模型訓練。

### 3.4. 情感分數轉換與預測

*   **需求 3 (部分)：** 模型輸出的情感分數 (0.0 ~ 1.0) 需轉換為三種情感類別：
    *   **正面 (1):** 當情感分數 > 0.66 (可調整閾值)
    *   **中性 (0):** 當 0.33 <= 情感分數 <= 0.66 (可調整閾值)
    *   **負面 (-1):** 當情感分數 < 0.33 (可調整閾值)
*   真實情感標籤也需進行統一：
    *   'positive' 標籤對應為 `1`。
    *   'negative' 標籤對應為 `-1`。
    *   (註：原 XML 資料似乎未直接提供「中性」標籤，需確認如何處理。一種可能是將所有非 'positive'/'negative' 的評論，或者基於某種規則，標記為中性，或是在模型訓練時僅考慮二分類「正面/負面」，然後在預測時引入「中性」的判斷區間。) *此處 PRD 假設以二分類為主，然後預測時根據分數閾值劃分出中性。*

### 3.5. 結果呈現與評估

*   **需求 4：** 命令列工具執行後，應針對 `data/Comments_Mobile_Phone.xml` 中的每一則評論 (或一個子集，用於展示)，在螢幕上印出：
    *   原始評論文字 (可選，用於對照)
    *   「真實情緒分數」(例如：positive -> 1, negative -> -1)
    *   「預測情緒分數」(轉換後的三分類：1 / 0 / -1)
*   **需求 5：** 在所有評論分析完成後，計算並印出整個模型在該資料集上的「準確度 (Accuracy)」。
    *   準確度 = (預測正確的評論數量) / (總評論數量)

### 3.6. 命令列介面 (CLI)

*   提供一個簡單的命令列介面來啟動分析過程。
*   例如，使用者可以直接執行 `python main.py` 或 `python analyze.py`。
*   不需要複雜的參數， क्योंकि資料來源固定為 `data/Comments_Mobile_Phone.xml`。

## 4. 建議技術棧

*   **程式語言:** Python 3.10+
*   **深度學習框架:** PyTorch
*   **XML 剖析:** BeautifulSoup4
*   **數值運算:** NumPy
*   **文字處理:** NLTK, spaCy (可選，依斷詞複雜度需求決定)
*   **依賴管理:** Poetry 或 Rye (建議)
*   **程式碼格式化:** Ruff

## 5. 資料處理流程

1.  **載入資料:** 從 `data/Comments_Mobile_Phone.xml` 讀取 XML。
2.  **剖析資料:** 使用 BeautifulSoup 提取評論文字和原始情感標籤。
3.  **清洗資料 (可選):** 移除不必要的 HTML 標籤、特殊字元等。
4.  **轉換標籤:** 將 'positive'/'negative' 標籤轉換為 `1`/`-1`。
5.  **斷詞:** 將評論文字分割成詞語。
6.  **建構詞彙表:** 根據所有詞語建立詞彙表，並將詞語映射到索引。
7.  **數位化序列:** 將每個評論的詞語序列轉換為數字索引序列。
8.  **序列對齊:** 將所有序列填充或截斷至相同長度。
9.  **資料分割 (可選):** 若要進行嚴謹的模型評估，可將資料集切分為訓練集、驗證集和測試集。對於本專案的初步目標 (分析整個 XML 並輸出結果)，可以先在完整資料上進行訓練與預測以展示結果。

## 6. 模型架構 (LSTM) - 初步構想

*   **嵌入層 (Embedding Layer):** 將數字索引序列轉換為密集詞向量。詞彙表大小和嵌入維度為超參數。
*   **LSTM 層:** 一層或多層 LSTM，捕捉序列中的時序依賴關係。隱藏單元數量為超參數。
*   **全連接層 (Linear Layer):** 將 LSTM 的輸出轉換為一個代表情感分數的單一數值 (0.0 ~ 1.0)。可使用 Sigmoid 激活函數確保輸出在該範圍內。
*   **Dropout (可選):** 在 LSTM 層或全連接層後加入 Dropout 以防止過擬合。

## 7. 評估指標與輸出格式

*   **主要評估指標:** 準確度 (Accuracy)。
*   **輸出格式 (CLI):**
    ```
    評論 1:
    真實情緒: 1 (positive)
    預測情緒: 1 (正面)

    評論 2:
    真實情緒: -1 (negative)
    預測情緒: 0 (中性)
    ...

    --------------------
    模型整體準確度: XX.XX%
    ```

## 8. 潛在挑戰與解決方案

*   **XML 結構不一致:** `Comments_Mobile_Phone.xml` 中不同評論的結構可能存在差異。
    *   **解決方案:** 在剖析階段編寫更具彈性的邏輯，或對特定結構進行假設並記錄。
*   **情感標籤的定義:** XML 中的 'positive'/'negative' 是否能完全對應到三分類中的「正面」和「負面」？「中性」評論如何界定？
    *   **解決方案:** 初期依照分數閾值劃分。若 XML 內有更細緻的標籤或分數，可加以利用。若無，則閾值法是合理起點。
*   **詞彙表外 (OOV) 問題:** 測試時出現訓練時未見過的詞語。
    *   **解決方案:** 使用 `<UNK>` (未知詞) 標記，或採用 Subword Tokenization (如 BPE, SentencePiece)。對於本專案的規模，簡單的 `<UNK>` 標記可能已足夠。
*   **計算資源:** 訓練 LSTM 模型可能需要一定的計算時間和記憶體。
    *   **解決方案:** 對於個人研究，可在 CPU 上運行，或使用 Google Colab 等免費 GPU 資源。模型規模和資料集大小也會影響資源需求。
